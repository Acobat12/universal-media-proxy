# Universal Media Proxy — установка на VPS за несколько минут

**Universal Media Proxy** — собственный сервер для получения аудио Bilibili и выдачи его по HTTP(S) с поддержкой `Range`. В проект также встроен **необязательный VOT-прокси**: оба сервиса могут работать на **одном VPS и одном домене**.

Проект **не переводит видео сам**. Перевод выполняет Яндекс; сервер только получает и отдаёт аудио и, при включении VOT-модуля, пересылает запросы к сервисам перевода. Совместимость с конкретной версией VOT и Bilibili нужно проверять отдельно.

## 1. Что понадобится

- VPS с **Ubuntu 22.04/24.04 или Debian 12**, доступ `root` или `sudo`, доступ в интернет.
- Рекомендуется **1 ГБ RAM**, 1 vCPU и 20 ГБ SSD для небольшого числа запросов.
- **Домен**, например `proxy.example.com`, для автоматического HTTPS. Создайте A-запись на IPv4 VPS. При наличии AAAA-записи она также должна указывать на работающий сервер. Откройте входящие TCP **80 и 443** в панели VPS/фаерволе.
- Можно использовать только **IP**, но установщик настроит в этом случае **обычный HTTP**; для VOT публичный HTTPS предпочтителен и может быть обязателен.

> **Безопасность:** скрипт скачивает пакеты из системных репозиториев, при необходимости подключает NodeSource для Node.js 22 и устанавливает Caddy. Прочитайте `install.sh` перед запуском. Скрипт предназначен для **чистого VPS**: в режиме домена он сохраняет резервную копию, а затем **заменяет** `/etc/caddy/Caddyfile`.

## 2. Установка напрямую с GitHub

После публикации файлов в репозитории **https://github.com/Acobat12/universal-media-proxy** войдите на Ubuntu/Debian VPS через SSH и выполните:

```bash
sudo apt-get update
sudo apt-get install -y git
git clone https://github.com/Acobat12/universal-media-proxy.git
cd universal-media-proxy
sudo bash install.sh
```

Больше ничего скачивать или распаковывать вручную не требуется. `git clone` скачает весь проект из GitHub; `install.sh` задаст вопросы и установит зависимости и службу.

> **Внимание:** репозиторий должен уже существовать и содержать файлы **в корне** (`install.sh`, `src/`, `package.json`). Пока репозиторий не опубликован, `git clone` вернёт ошибку. Прочитайте `install.sh` перед запуском, поскольку он выполняется с правами `root`.

### Ещё короче (если Git уже установлен)

```bash
git clone https://github.com/Acobat12/universal-media-proxy.git && cd universal-media-proxy && sudo bash install.sh
```

### Если у вас только чистый VPS

1. Подключитесь к серверу командой `ssh root@IP_СЕРВЕРА` (или используйте SSH-пользователя с `sudo`).
2. Выполните четыре команды из блока выше.
3. Введите домен или IP, настройки VOT и лимит SSD-кэша.
4. По окончании проверьте адрес `/health`.

С доменом установщик настроит HTTPS через Caddy, если DNS уже указывает на сервер и открыты порты 80/443. С IP используется HTTP — для полноценной совместимости с VOT рекомендуется домен.

### Какие вопросы задаст установщик

1. **Домен или IP?** Например, `proxy.example.com`.
2. Если указан IP — **HTTP-порт**, по умолчанию `3000`.
3. При домене — подтверждение настройки HTTPS.
4. **Включить VOT-прокси?** Можно выбрать `y`.
5. **Лимит SSD-кэша** в МиБ, по умолчанию `1024` (1 ГиБ).
6. Подтверждение установки Node.js и системной службы.

Установщик сам создаст случайные `TOKEN_SECRET`, `API_KEY` и `VOT_PROXY_API_KEY`, создаст отдельного системного пользователя, настроит `systemd`, SSD-кэш и при домене — Caddy с автоматическим HTTPS. Ключи будут показаны в конце и сохранены в `/etc/universal-media-proxy.env` с правами доступа только для root.

**Важно:** скрипт не настраивает DNS-записи у регистратора и не открывает порты в панели VPS. Сертификат Let's Encrypt выдаётся Caddy при выполнении сетевых условий; успешное выполнение установщика само по себе не гарантирует выдачу сертификата.

## 4. Получение ссылки на аудио Bilibili

Вместо `YOUR_API_KEY` подставьте ключ, который вывел установщик; вместо `BV...` — реальный BVID.

```bash
curl -X POST 'https://proxy.example.com/api/resolve' \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: YOUR_API_KEY' \
  -d '{"url":"https://www.bilibili.com/video/BV...","quality":"best","mode":"disk"}'
```

Ответ содержит `mediaUrl` — подписанную временную ссылку на аудио. Её можно передать клиенту, который умеет загружать аудио по HTTP(S). Само по себе получение ссылки **не запускает перевод**.

Проверка ссылки (вставьте реальный URL):

```bash
curl -I 'https://proxy.example.com/media/ВАШ_ТОКЕН'
curl -H 'Range: bytes=0-1023' -o first-1k.bin 'https://proxy.example.com/media/ВАШ_ТОКЕН'
```

При частичной выдаче ожидается `206 Partial Content` и корректный `Content-Range`. Ссылки содержат токен доступа: не публикуйте их без необходимости.

## 5. SSD-кэш: 15 минут и автоматическое удаление

По умолчанию установщик задаёт:

```dotenv
DEFAULT_AUDIO_MODE=disk
DISK_CACHE_DIR=/var/cache/universal-media-proxy
DISK_CACHE_TTL_MS=900000
DISK_CACHE_MAX_BYTES=1073741824
DISK_CACHE_MAX_FILE_BYTES=268435456
PARALLEL_THREADS=8
PARALLEL_CHUNK_BYTES=524288
```

`900000` мс = **15 минут**. Аудио скачивается на SSD, а не хранится целиком в RAM. Кэш ограничен по общему размеру и по размеру отдельного файла. Удаление просроченных файлов зависит от механизма очистки приложения и активных запросов; **не следует считать TTL гарантией удаления ровно в указанную секунду**. Окончание перевода Яндекса сервер определить не может.

Режимы: `stream` — напрямую без полной загрузки; `parallel` — параллельные диапазоны с потоковой выдачей; `cached` — временный кэш в RAM; `disk` — временный кэш на SSD. Для недорогого VPS начните с `disk`, а если возникают задержки перед началом перевода, сравните со `stream`.

## 6. Два разных прокси на одном VPS: аудио Bilibili и API Яндекса

На одном сервере работают **два независимых механизма**. Они используют общий HTTPS-домен и порт, но выполняют разные задачи.

```text
                        ВАШ VPS: https://proxy.example.com
                        │
        ┌───────────────┴───────────────────────────────┐
        │                                               │
  ① Media Proxy                                  ② VOT API Proxy
  POST /api/resolve                              POST /vot/video-translation/translate
  GET  /media/<token>                            POST /vot/session/create
        │                                               │
        ▼                                               ▼
  Bilibili CDN                                  api.browser.yandex.ru
        │                                               │
  временный SSD-кэш                              ответ API Яндекса
  (15 минут)                                          │
        │                                               ▼
        └── аудио по HTTPS ──► VOT-клиент / сервис перевода
```

**① Media Proxy** получает ссылку на DASH-аудио Bilibili, при режиме `disk` загружает файл на SSD и предоставляет `mediaUrl` с поддержкой HTTP Range. Этот механизм не выполняет перевод.

**② VOT API Proxy** принимает запросы клиента перевода, направляет их к API Яндекса и возвращает ответ. Это **не** альтернативный загрузчик Bilibili-аудио и **не** собственный движок распознавания речи. Доступ к Яндексу, корректные параметры запроса, подписи и совместимость клиента по-прежнему необходимы.

### 6.1. Как VOT-прокси обращается к Яндексу

Когда клиент поддерживаемой версии отправляет запрос на:

```text
POST https://proxy.example.com/vot/video-translation/translate
```

сервер выполняет следующую последовательность:

1. Проверяет, что `ENABLE_VOT_PROXY=true` и путь разрешён.
2. Если задан `VOT_PROXY_API_KEY`, проверяет заголовок `X-Proxy-Key`.
3. Ограничивает размер тела запроса (`VOT_MAX_BODY_BYTES`).
4. Обрабатывает **Protobuf envelope** (`application/x-vot-envelope+protobuf`) либо двухшаговую схему с предварительной передачей метаданных. Для обычного JSON этот маршрут **не предназначен**.
5. Пересылает сформированный запрос на `https://api.browser.yandex.ru/video-translation/translate` (или на адрес `YANDEX_API_URL`, если он явно задан).
6. Возвращает ответ API клиенту. Если Яндекс отказывает или клиент сформировал некорректный запрос, прокси не может сам устранить причину.

Важное отличие: **переадресация URL не равнозначна поддержке протокола**. Обычный `curl` с JSON и URL видео не создаёт корректный запрос перевода; требуются данные и заголовки, которые формирует совместимый VOT-клиент.

### 6.2. Какие адреса доступны

| Метод | Адрес на вашем сервере | Назначение |
|---|---|---|
| `POST` | `/vot/video-translation/translate` | Запрос перевода через API Яндекса |
| `POST` | `/vot/video-translation/cache` | Операции кэша перевода через API Яндекса |
| `POST` | `/vot/session/create` | Создание сессии |
| `POST` | `/vot/video-subtitles/get-subtitles` | Запрос субтитров |
| `POST` | `/vot/stream-translation/translate-stream` | Запрос потокового перевода |
| `POST` | `/vot/stream-translation/ping-stream` | Проверка потоковой сессии |
| `PUT` | `/vot/video-translation/audio` | Операция с аудио через API Яндекса |
| `PUT` | `/vot/video-translation/fail-audio-js` | Сообщение об ошибке аудио |
| `GET`, `HEAD` | `/vot/video-translation/audio-proxy/…mp3` | Получение готового аудио перевода из хранилища Яндекса |
| `GET`, `HEAD` | `/vot/video-subtitles/subtitles-proxy/…` | Получение субтитров из хранилища Яндекса |
| `POST` | `/vot/metadata` | Передача метаданных двухшагового протокола |

**Не путайте** `/media/<token>` (исходное аудио Bilibili, временно лежащее на вашем SSD) с `/vot/video-translation/audio-proxy/…` (аудио **перевода**, которое сервер запрашивает у инфраструктуры Яндекса). 15-минутный SSD-кэш относится к первому случаю, а не ко всем ответам Яндекса.

### 6.3. Как включить VOT API Proxy

При запуске `sudo bash install.sh` ответьте **`y`** на вопрос «Включить VOT-прокси на этом же сервере?». Установщик добавит в `/etc/universal-media-proxy.env`:

```dotenv
ENABLE_VOT_PROXY=true
VOT_PROXY_API_KEY=СЛУЧАЙНЫЙ_КЛЮЧ_ИЗ_УСТАНОВЩИКА
VOT_MAX_BODY_BYTES=1048576
```

При необходимости после установки можно указать `YANDEX_API_URL=https://api.browser.yandex.ru`. Если переменная отсутствует, этот адрес используется по умолчанию. Менять его на произвольный недоверенный сервер не следует: туда передаются данные запросов перевода.

Чтобы изменить параметры:

```bash
sudo nano /etc/universal-media-proxy.env
sudo systemctl restart universal-media-proxy
```

### 6.4. Как изменить код VOT для работы через свой прокси

В разных версиях VOT имена файлов отличаются. **Не заменяйте файлы из чужой версии целиком.** Найдите места создания API-клиента, хранения настроек и обработки аудио/субтитров; добавьте логику по инструкции **[docs/VOT_CODE_CHANGES_RU.md](docs/VOT_CODE_CHANGES_RU.md) (включая полный код `VOTProtobufEnvelopeProvider` и его подключение)**. Там приведены конкретные фрагменты TypeScript, что искать и что менять, включая необязательный Protobuf Envelope.

### 6.5. Проверка без настоящего перевода

Проверить доступность самого сервера:

```bash
curl -i https://proxy.example.com/health
```

Проверить, что защищённый VOT-маршрут **отказывает без ключа**:

```bash
curl -i -X POST https://proxy.example.com/vot/video-translation/translate
```

При включённом `VOT_PROXY_API_KEY` ожидается `401 Unauthorized`. Это хороший признак работы проверки доступа, **но не подтверждение успешного перевода**.

Проверить, что сервер принимает ключ и затем проверяет тип данных:

```bash
curl -i -X POST https://proxy.example.com/vot/video-translation/translate \
  -H 'X-Proxy-Key: ВАШ_VOT_PROXY_API_KEY' \
  -H 'Content-Type: application/json' \
  --data '{}'
```

Для этого маршрута JSON не является допустимым форматом. Встроенный обработчик может вернуть `204` с диагностическим заголовком `X-Yandex-Status: error-content`. Это **не успешный перевод**, а проверка обработки неподходящего запроса.

Журнал работы:

```bash
sudo journalctl -u universal-media-proxy -f
```

Не публикуйте реальные ключи, подписанные запросы и приватные заголовки из логов.

### 6.6. Ограничения и безопасность

- Яндекс может изменять API, требовать актуальные подписи, токены, специфичные заголовки и отклонять запросы с VPS.
- Прокси пересылает запросы, но **не создаёт самостоятельно** недостающие авторизационные данные клиента.
- Параметр `VOT_PROXY_API_KEY` защищает входящие запросы к VPS; он **не является** ключом доступа к API Яндекса.
- Реальная связка Bilibili → Media Proxy → VOT API Proxy → Яндекс не проверена сквозным тестом; локальные тесты проверяют лишь отдельные маршруты и логику.
- Не рекомендуется делать VOT API Proxy публичным без контроля доступа, сетевых лимитов и наблюдения за расходом трафика.

## 7. Изменить настройки после установки

```bash
sudo nano /etc/universal-media-proxy.env
sudo systemctl restart universal-media-proxy
```

Важные переменные:

| Переменная | Назначение |
|---|---|
| `PUBLIC_BASE_URL` | Публичный URL сервера, например `https://proxy.example.com` |
| `HOST` / `PORT` | Локальный адрес и порт Node.js |
| `DEFAULT_AUDIO_MODE` | `stream`, `parallel`, `cached`, `disk` |
| `DISK_CACHE_TTL_MS` | Срок SSD-кэша в миллисекундах |
| `DISK_CACHE_MAX_BYTES` | Максимальный размер всего SSD-кэша |
| `DISK_CACHE_MAX_FILE_BYTES` | Максимальный размер одного файла |
| `MAX_CONCURRENT_STREAMS` | Число одновременных выдач |
| `ENABLE_VOT_PROXY` | Включение маршрутов `/vot/*` |
| `VOT_PROXY_API_KEY` | Ключ доступа к VOT-прокси |
| `ENABLE_YTDLP` | Необязательный резервный извлекатель, по умолчанию выключен |

Установщик **предлагает сразу установить yt-dlp из официальных GitHub Releases**. По умолчанию выбран ответ **Да**: установщик загружает исполняемый файл `yt-dlp`, сверяет SHA-256 с опубликованным в релизе `SHA2-256SUMS`, помещает его в `/usr/local/bin/yt-dlp` и включает резервное извлечение для **Bilibili**. Установка `python3` выполняется автоматически.

При запросе установщика можно ответить `n` и оставить `yt-dlp` выключенным. По умолчанию разрешён только `bilibili.com` (включая поддомены); добавление других сайтов в `YTDLP_ALLOWED_HOSTS` и `ALLOWED_UPSTREAM_HOSTS` требует проверки безопасности и поддержки прямых HTTPS-аудиопотоков. `yt-dlp` — внешний исполняемый файл, поэтому используйте его только с доверенными URL и своевременно обновляйте.

**Обновление yt-dlp:** новые версии не устанавливаются автоматически. При необходимости загрузите свежий официальный релиз с повторной проверкой SHA-256. Для ручной диагностики: `yt-dlp --version` и `sudo journalctl -u universal-media-proxy -n 100 --no-pager`. Некоторые сайты могут требовать дополнительные зависимости или авторизацию; установка `yt-dlp` не гарантирует успешное извлечение всех видео.

## 9. Получение обновлений с GitHub

Установщик не перезаписывает существующую конфигурацию и **не предназначен для повторного запуска поверх установленного сервера**. Для обновления кода из GitHub:

```bash
cd ~/universal-media-proxy
git pull --ff-only
npm test
sudo cp -a src package.json /opt/universal-media-proxy/
sudo chown -R root:root /opt/universal-media-proxy
sudo systemctl restart universal-media-proxy
sudo systemctl status universal-media-proxy
```

Если репозиторий был клонирован в другую директорию, перейдите в неё вместо `~/universal-media-proxy`. Перед обновлением проверьте релизные замечания: если новая версия меняет переменные окружения или зависимости, простой заменой `src` и `package.json` обновление может не ограничиться.

## 10. Удаление



Перед обновлением сделайте резервную копию конфигурации. **Повторный запуск `install.sh` поверх установленного сервера намеренно блокируется**, чтобы не перезаписать ключи. Для ручного обновления перенесите новые `src` и `package.json` в `/opt/universal-media-proxy`, затем перезапустите службу. Следите за совместимостью конфигурации и делайте резервную копию.

Для удаления остановите и отключите службу, удалите её unit-файл, код, настройки и кэш. **Не удаляйте Caddy**, если его используют другие сайты. Удаление каталога кэша безвозвратно удалит загруженные аудиофайлы.

## 11. Ограничения и безопасность

- API-ключ защищает `/api/resolve`; подписанный `mediaUrl` может использовать каждый, у кого есть ссылка, пока токен действителен.
- Не делайте VOT-прокси общедоступным без проверки ключа и ограничения запросов. Дополнительно ограничьте доступ на уровне Caddy или сетевого фаервола.
- Квоты передачи в текущей версии учитываются процессом Node.js и могут сбрасываться при перезапуске.
- Bilibili может менять API, ограничивать CDN, требовать cookies/WBI-подпись или блокировать IP сервера.
- При использовании CDN оплачивается **исходящий трафик VPS**, если он не включён в тариф.
- Для публичной эксплуатации нужны дополнительные нагрузочные, сетевые и интеграционные испытания.
- Проверяйте соблюдение условий использования источников и применимого законодательства.

## 12. Разработка и тесты

Для локального запуска требуется Node.js **22+**:

```bash
npm test
npm run check
```

Сервер запускается через `npm start` после установки переменных окружения (сам Node.js файл `.env` автоматически не загружает). На VPS это делает `systemd` через `EnvironmentFile`.

Проект включает код Bilibili-адаптера, потокового прокси, параллельного загрузчика, RAM/SSD-кэша и VOT-шлюза. Лицензия MIT — см. `LICENSE`.
