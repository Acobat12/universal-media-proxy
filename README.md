# Universal Media Proxy (UMP) — универсальный медиапрокси для VPS

**Universal Media Proxy (UMP)** — расширяемый сервер для получения, подготовки и выдачи медиа по HTTP(S). Поддерживает подключаемые адаптеры сайтов, стабильные медиаадреса там, где их реализует адаптер, HTTP Range, потоковую и параллельную передачу, временное хранение на SSD. Необязательный **VOT API Proxy** может работать на том же VPS и домене.

Проект **не переводит видео сам**: перевод выполняет внешний сервис Яндекса. UMP выдаёт исходное медиа и при включении VOT-модуля пересылает запросы к сервису перевода. Совместимость с конкретными сайтами, версиями VOT и методами авторизации необходимо проверять отдельно.

**Адаптеры в проверяемой версии:** Bilibili, Douyin, TikTok, Coub, Cloud Mail.ru, NHK WORLD и NHK Japan. Наличие адаптера означает поддержку определённых сценариев, **не гарантию** работы любого видео, прямой ссылки, cookies, DRM или регионально ограниченного контента. Список реально загруженных адаптеров показывает `GET /health`. Новые сайты добавляются адаптерами без необходимости встраивать их в ядро UMP.

## 1. Что понадобится

- VPS с **Ubuntu 22.04/24.04 или Debian 12**, доступ `root` или `sudo`, доступ в интернет.
- Рекомендуется **1 ГБ RAM**, 1 vCPU и 20 ГБ SSD для небольшого числа запросов.
- Бесплатный поддомен можно получить на [DuckDNS](https://www.duckdns.org/) или [FreeDNS](https://freedns.afraid.org/). Укажите IP своего VPS в DNS и дождитесь обновления записи. Для работы VOT используйте HTTPS.
- **Домен**, например `proxy.example.com`, для автоматического HTTPS. Создайте A-запись на IPv4 VPS. При наличии AAAA-записи она также должна указывать на работающий сервер. Откройте входящие TCP **80 и 443** в панели VPS/фаерволе.
- Можно использовать только **IP**, но установщик настроит в этом случае **обычный HTTP**; для VOT публичный HTTPS предпочтителен и может быть обязателен.

> **Безопасность:** скрипт скачивает пакеты из системных репозиториев, при необходимости подключает NodeSource для Node.js 22 и устанавливает Caddy. Прочитайте `install.sh` перед запуском. Скрипт предназначен для **чистого VPS**: в режиме домена он сохраняет резервную копию, а затем **заменяет** `/etc/caddy/Caddyfile`.

### 3.1. Авторизация TikTok через noVNC + Chromium (интерактивный вход на VPS)

Этот способ позволяет открыть **настоящий Chromium на VPS**, войти в TikTok привычным способом (пароль, QR-код или другой вариант, предлагаемый сайтом) и сохранить авторизованную сессию в постоянном браузерном профиле. Браузер отображается на компьютере через **noVNC**, а соединение защищено **SSH-туннелем**. Пароль TikTok не нужно вводить в терминале или конфигурации UMP.

**Предварительные условия:** UMP уже установлен; на VPS установлены Chromium/Playwright, Xvfb, x11vnc, websockify и noVNC; команда `ump-browser` доступна. Это **дополнительный режим для сборок, где установлен `ump-browser`**, а не гарантированная возможность любой версии репозитория. Проверьте:

```bash
command -v ump-browser
sudo ump-browser list
```

Если команда отсутствует, сначала установите совместимые компоненты браузерной авторизации для своей версии UMP. **Не запускайте `install.sh` повторно поверх действующей установки** только ради этой функции.

#### Шаг 1. Запустите авторизацию на VPS

Подключитесь к серверу по SSH и выполните:

```bash
sudo ump-browser login tiktok
```

При успешном запуске команда напечатает инструкцию для SSH-туннеля и адрес noVNC. **Оставьте этот терминал открытым**: сессия работает, пока выполняется команда (в текущей реализации — до 20 минут или до `Ctrl+C`). Для TikTok скрипт временно останавливает `universal-media-proxy.service`, чтобы не допустить одновременного использования одного Chromium-профиля.

#### Шаг 2. Создайте SSH-туннель на Windows

На **своём компьютере с Windows** откройте новое окно CMD или PowerShell и выполните команду, которую вывел `ump-browser`. Например, при порте SSH `22` и порте noVNC `16080`:

```powershell
ssh -N -L 16080:127.0.0.1:16080 -p 22 root@IP_ВАШЕГО_VPS
```

Замените `IP_ВАШЕГО_VPS` и порт SSH на свои значения. Введите пароль SSH или используйте настроенный SSH-ключ. **После успешного входа окно может остаться пустым — это нормально:** параметр `-N` создаёт туннель и не открывает командную оболочку. **Не закрывайте это окно**, пока используете noVNC.

#### Шаг 3. Откройте TikTok через noVNC

В Chrome или Edge **на Windows** откройте адрес, показанный скриптом, например:

```text
http://127.0.0.1:16080/vnc.html
```

Нажмите **«Подключение» / Connect**. На виртуальном экране VPS должно появиться окно Chromium с TikTok. Если сначала видна только страница noVNC, это ещё не экран браузера — необходимо нажать кнопку подключения. В TikTok нажмите **Log in / Войти**, выполните авторизацию и убедитесь, что сайт показывает ваш аккаунт.

> **Важно:** адрес `127.0.0.1` в браузере Windows относится к вашему компьютеру; SSH-туннель передаёт запросы на VPS. **Не открывайте публично порты `15900` (VNC) и `16080` (noVNC)** в UFW, панели хостинга или роутере. Сервисы должны слушать только loopback-адреса. Не передавайте посторонним доступ к активной браузерной сессии.

#### Шаг 4. Завершите сессию и проверьте UMP

После успешного входа **не нажимайте Logout / Выйти на сайте TikTok**. Вернитесь в терминал VPS, где выполняется `sudo ump-browser login tiktok`, и нажмите **`Ctrl+C`**. Это завершит браузерную сессию, освободит профиль и позволит скрипту снова запустить UMP. Затем проверьте:

```bash
systemctl is-active universal-media-proxy.service
sudo journalctl -u universal-media-proxy.service -n 30 --no-pager
sudo ls -ld /var/cache/universal-media-proxy/tiktok-profile
```

Ожидается `active`; владельцем профиля должен быть `ump:ump`. Профиль TikTok по умолчанию расположен здесь:

```text
/var/cache/universal-media-proxy/tiktok-profile
```

Cookies и другие данные сеанса сохраняются в профиле Chromium и могут использоваться при следующих запусках. В текущем адаптере путь к нему задаётся переменной `TIKTOK_PROFILE_DIR` либо указанным путём по умолчанию. **Успешный вход не гарантирует успешного получения каждого видео**: сайт может изменить требования, ограничить доступ или потребовать повторную авторизацию.

#### Если что-то не работает

- **После ввода пароля SSH «ничего не происходит».** Для `ssh -N` это штатное поведение. Оставьте CMD/PowerShell открытым и перейдите к адресу noVNC.
- **Страница noVNC открылась, но TikTok не виден.** Нажмите **«Подключение»**. Если экран пустой, во втором SSH-сеансе проверьте процессы и окна виртуального экрана:

  ```bash
  ps -eo user,pid,stat,args | grep -E '[X]vfb|[x]11vnc|[w]ebsockify|[c]hrome'
  sudo ss -lntp | grep -E '15900|16080'
  sudo env DISPLAY=:97 xwininfo -root -tree | head -n 25
  ```

  `:97` — пример номера дисплея из конкретной сессии; используйте фактический `DISPLAY`, если он отличается. Если `xwininfo` отсутствует, установите пакет `x11-utils`.
- **Chromium завершился с `chrome_crashpad_handler: --database is required` или `SIGTRAP`.** Проверьте, что пользователь `ump` имеет право записи в домашний каталог браузерной сессии. Для данной конфигурации используется отдельный каталог:

  ```bash
  sudo install -d -o ump -g ump -m 700 /var/cache/universal-media-proxy/browser-home
  sudo install -d -o ump -g ump -m 700 /var/cache/universal-media-proxy/browser-home/.config
  sudo install -d -o ump -g ump -m 700 /var/cache/universal-media-proxy/browser-home/.cache
  grep 'HOME=' /usr/local/bin/ump-browser
  ```

  В команде запуска Playwright должно быть `HOME=/var/cache/universal-media-proxy/browser-home`. Не меняйте владельца всего каталога `/opt/universal-media-proxy` рекурсивно.
- **`ump-browser` сразу завершился с кодом `141`.** Возможная причина — `SIGPIPE` при `set -o pipefail` и преждевременном завершении `awk` в конвейере `sshd -T`. Для диагностики:

  ```bash
  sudo bash -x /usr/local/bin/ump-browser login tiktok > /tmp/ump-browser-debug.log 2>&1
  echo "Код завершения: $?"
  tail -n 45 /tmp/ump-browser-debug.log
  ```

  В исправленной реализации чтение порта SSH не должно преждевременно закрывать конвейер, например `awk '$1=="port" && !found {print $2; found=1}'` вместо `awk '$1=="port" {print $2; exit}'`.
- **В журнале `"registrations":0`.** Это количество действующих временных регистраций **видео** из `tiktok-registrations.json`, а не число авторизованных аккаунтов и не показатель наличия cookies. Ноль сам по себе не означает ошибку входа.

**Безопасность и резервные копии:** браузерный профиль содержит чувствительные данные авторизации. Не публикуйте его, не отправляйте cookies в отчётах об ошибках и не удаляйте `/var/cache/universal-media-proxy` целиком при очистке медиакэша. При обновлении или переустановке отдельно сохраняйте профиль и другие постоянные данные.

## 4. Получение медиа через адаптеры

Единый API `POST /api/resolve` выбирает адаптер по исходному URL. Ниже — **пример для Bilibili**, а не ограничение UMP одним сайтом. Для других источников передайте URL, поддерживаемый соответствующим адаптером. Набор доступных маршрутов и режимов зависит от реализации адаптера.

```bash
curl -X POST 'https://proxy.example.com/api/resolve' \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://www.bilibili.com/video/BV...","quality":"best","mode":"disk"}'
```

При поддержке соответствующего сценария ответ содержит `mediaUrl` — адрес медиа, формируемый адаптером. Стабильность URL и восстановление источника после перезапуска зависят от конкретного адаптера. Её можно передать клиенту, который умеет загружать аудио по HTTP(S). Само по себе получение ссылки **не запускает перевод**.

Проверка ссылки (вставьте реальный URL):

```bash
curl -I 'https://proxy.example.com/media/bilibili/BV18b411q7Fb/p1/audio.m4a'
curl -H 'Range: bytes=0-1023' -o first-1k.bin 'https://proxy.example.com/media/bilibili/BV18b411q7Fb/p1/audio.m4a'
```

При частичной выдаче ожидается `206 Partial Content` и корректный `Content-Range`. Стабильные медиаадреса не требуют временных токенов, когда адаптер умеет восстановить источник. Для некоторых сайтов нужны предварительная регистрация, cookies или отдельный маршрут.

## 5. Общее временное хранилище медиа (SSD)

По умолчанию установщик задаёт:

```dotenv
DEFAULT_AUDIO_MODE=disk
DISK_CACHE_DIR=/var/cache/universal-media-proxy/media
DISK_CACHE_TTL_MS=900000
DISK_CACHE_MAX_BYTES=1073741824
DISK_CACHE_MAX_FILE_BYTES=268435456
DISK_CACHE_MIN_FREE_BYTES=134217728
PARALLEL_THREADS=8
PARALLEL_CHUNK_BYTES=524288
```

`900000` мс = **15 минут**. Аудио скачивается на SSD, а не хранится целиком в RAM. Общий размер — **мягкая целевая граница**: при параллельной записи и конвертации возможно временное превышение. Отдельные пути, временные файлы и процессы FFmpeg должны корректно регистрироваться адаптерами, иначе их очистка и защита от удаления могут быть неполными. Удаление просроченных файлов зависит от механизма очистки приложения и активных запросов; **не следует считать TTL гарантией удаления ровно в указанную секунду**. Окончание перевода Яндекса сервер определить не может.

Режимы: `stream` — напрямую без полной загрузки; `parallel` — параллельные диапазоны с потоковой выдачей; `cached` — временный кэш в RAM; `disk` — временный кэш на SSD. Для недорогого VPS начните с `disk`, а если возникают задержки перед началом перевода, сравните со `stream`.

## 6. Медиапрокси для разных сайтов и отдельный VOT API Proxy

На одном сервере работают **два независимых механизма**. Первый обслуживает медиа разных сайтов через адаптеры, второй пересылает запросы перевода. Они могут использовать один HTTPS-домен и порт.

```text
                        ВАШ VPS: https://proxy.example.com
                        │
        ┌───────────────┴───────────────────────────────┐
        │                                               │
  ① Universal Media Proxy                                  ② VOT API Proxy
  POST /api/resolve                              POST /vot/video-translation/translate
  GET  /media/bilibili/BVID/p1/audio.m4a                            POST /vot/session/create
        │                                               │
        ▼                                               ▼
  CDN поддерживаемых сайтов                                  api.browser.yandex.ru
        │                                               │
  временный SSD-кэш                              ответ API Яндекса
  (15 минут)                                          │
        │                                               ▼
        └── аудио по HTTPS ──► VOT-клиент / сервис перевода
```

**① Universal Media Proxy** получает ссылку на DASH-аудио Bilibili, при режиме `disk` загружает файл на SSD и предоставляет `mediaUrl` с поддержкой HTTP Range. Этот механизм не выполняет перевод.

**② VOT API Proxy** принимает запросы клиента перевода, направляет их к API Яндекса и возвращает ответ. Это **не** альтернативный загрузчик Bilibili-аудио и **не** собственный движок распознавания речи. Доступ к Яндексу, корректные параметры запроса, подписи и совместимость клиента по-прежнему необходимы.

### 6.1. Как VOT-прокси обращается к Яндексу

Когда клиент поддерживаемой версии отправляет запрос на:

```text
POST https://proxy.example.com/vot/video-translation/translate
```

сервер выполняет следующую последовательность:

1. Проверяет, что `ENABLE_VOT_PROXY=true` и путь разрешён.
2. Не требует `X-Proxy-Key`: VOT API общедоступен.
3. Ограничивает размер тела запроса (`VOT_MAX_BODY_BYTES`).
4. Обрабатывает **Protobuf envelope** (`application/x-vot-envelope+protobuf`) либо двухшаговую схему с предварительной передачей метаданных. Для обычного JSON этот маршрут **не предназначен**.
5. Пересылает сформированный запрос на `https://api.browser.yandex.ru/video-translation/translate` (или на адрес `YANDEX_API_URL`, если он явно задан).
6. Возвращает ответ API клиенту. Если Яндекс отказывает или клиент сформировал некорректный запрос, прокси не может сам устранить причину.

Важное отличие: **переадресация URL не равнозначна поддержке протокола**. Обычный `curl` с JSON и URL видео не создаёт корректный запрос перевода; требуются данные и заголовки, которые формирует совместимый VOT-клиент.

### 6.2. Какие адреса доступны

| Метод | Адрес на вашем сервере | Назначение |
|---|---|---|
| `POST` | `/vot/video-translation/translate` | Запрос перевода через API Яндекса |
| `POST` | `/vot/video-translation/cache` | Операции кэша перевода через API Яндекса |
| `POST` | `/vot/session/create` | Создание сессии |
| `POST` | `/vot/video-subtitles/get-subtitles` | Запрос субтитров |
| `POST` | `/vot/stream-translation/translate-stream` | Запрос потокового перевода |
| `POST` | `/vot/stream-translation/ping-stream` | Проверка потоковой сессии |
| `PUT` | `/vot/video-translation/audio` | Операция с аудио через API Яндекса |
| `PUT` | `/vot/video-translation/fail-audio-js` | Сообщение об ошибке аудио |
| `GET`, `HEAD` | `/vot/video-translation/audio-proxy/…mp3` | Получение готового аудио перевода из хранилища Яндекса |
| `GET`, `HEAD` | `/vot/video-subtitles/subtitles-proxy/…` | Получение субтитров из хранилища Яндекса |
| `POST` | `/vot/metadata` | Передача метаданных двухшагового протокола |

**Не путайте** `/media/bilibili/BVID/p1/audio.m4a` (стабильный адрес исходного аудио Bilibili) с `/vot/video-translation/audio-proxy/…` (аудио **перевода**, которое сервер запрашивает у инфраструктуры Яндекса). 15-минутный SSD-кэш относится к первому случаю, а не ко всем ответам Яндекса.

### 6.3. Как включить VOT API Proxy

При запуске `sudo bash install.sh` ответьте **`y`** на вопрос «Включить VOT-прокси на этом же сервере?». Установщик добавит в `/etc/universal-media-proxy.env`:

```dotenv
ENABLE_VOT_PROXY=true
VOT_MAX_BODY_BYTES=1048576
```

При необходимости после установки можно указать `YANDEX_API_URL=https://api.browser.yandex.ru`. Если переменная отсутствует, этот адрес используется по умолчанию. Менять его на произвольный недоверенный сервер не следует: туда передаются данные запросов перевода.

Чтобы изменить параметры:

```bash
sudo nano /etc/universal-media-proxy.env
sudo systemctl restart universal-media-proxy
```

### 6.4. Как изменить код VOT для работы через свой прокси

В разных версиях VOT имена файлов отличаются. **Не заменяйте файлы из чужой версии целиком.** Найдите места создания API-клиента, хранения настроек и обработки аудио/субтитров; добавьте логику по инструкции **[docs/VOT_CODE_CHANGES_RU.md](docs/VOT_CODE_CHANGES_RU.md) (включая полный код `VOTProtobufEnvelopeProvider` и его подключение)**. Там приведены конкретные фрагменты TypeScript, что искать и что менять, включая необязательный Protobuf Envelope.

### 6.5. Проверка без настоящего перевода

Проверить доступность самого сервера:

```bash
curl -i https://proxy.example.com/health
```

Проверить публичный VOT-маршрут без ключа:

```bash
curl -i -X POST https://proxy.example.com/vot/video-translation/translate
```

Ответ не должен быть `401` из-за отсутствия `X-Proxy-Key`. Это **не подтверждение успешного перевода**.

Проверить обработку запроса без ключа:

```bash
curl -i -X POST https://proxy.example.com/vot/video-translation/translate \
  -H 'Content-Type: application/json' \
  --data '{}'
```

Для этого маршрута JSON не является допустимым форматом. Встроенный обработчик может вернуть `204` с диагностическим заголовком `X-Yandex-Status: error-content`. Это **не успешный перевод**, а проверка обработки неподходящего запроса.

Журнал работы:

```bash
sudo journalctl -u universal-media-proxy -f
```

Не публикуйте реальные ключи, подписанные запросы и приватные заголовки из логов.

### 6.6. Ограничения и безопасность

- Яндекс может изменять API, требовать актуальные подписи, токены, специфичные заголовки и отклонять запросы с VPS.
- Прокси пересылает запросы, но **не создаёт самостоятельно** недостающие авторизационные данные клиента.
- VOT API открыт без ключа для всех; публичный сервер может потреблять значительный трафик и ресурсы.
- Проверена отправка VOT Protobuf Envelope: Cloudflare Worker получил HTTP 200 от Яндекса, а VPS — HTTP 402 при совпадающем SHA-256 тела. Причина различия не установлена. Сквозной сценарий Bilibili → Media Proxy → VOT не подтверждён.
- VOT API Proxy публичен по запросу владельца; отслеживайте расход трафика и ресурсов.

## 7. Изменение настроек после установки

```bash
sudo nano /etc/universal-media-proxy.env
sudo systemctl restart universal-media-proxy
```

Важные переменные:

| Переменная | Назначение |
|---|---|
| `PUBLIC_BASE_URL` | Публичный URL сервера, например `https://proxy.example.com` |
| `HOST` / `PORT` | Локальный адрес и порт Node.js |
| `DEFAULT_AUDIO_MODE` | `stream`, `parallel`, `cached`, `disk` |
| `DISK_CACHE_TTL_MS` | Срок SSD-кэша в миллисекундах |
| `DISK_CACHE_MAX_BYTES` | Максимальный размер всего SSD-кэша |
| `DISK_CACHE_MAX_FILE_BYTES` | Максимальный размер одного кешируемого файла |
| `DISK_CACHE_MIN_FREE_BYTES` | Минимальный запас свободного места на диске |
| `DISK_CACHE_DIR` | Каталог временных медиафайлов, **не** регистраций и cookies |
| `MAX_CONCURRENT_STREAMS` | Число одновременных выдач |
| `ENABLE_VOT_PROXY` | Включает публичные маршруты `/vot/*` без ключа |
| `ENABLE_YTDLP` | Необязательный резервный извлекатель, по умолчанию выключен |

Установщик **предлагает сразу установить yt-dlp из официальных GitHub Releases**. По умолчанию выбран ответ **Да**: установщик загружает исполняемый файл `yt-dlp`, сверяет SHA-256 с опубликованным в релизе `SHA2-256SUMS`, помещает его в `/usr/local/bin/yt-dlp` и включает резервное извлечение для **Bilibili в текущей конфигурации**. Это ограничение конкретного резервного механизма, **не список всех сайтов UMP**. Установка `python3` выполняется автоматически.

При запросе установщика можно ответить `n` и оставить `yt-dlp` выключенным. По умолчанию разрешён только `bilibili.com` (включая поддомены); добавление других сайтов в `YTDLP_ALLOWED_HOSTS` и `ALLOWED_UPSTREAM_HOSTS` требует проверки безопасности и поддержки прямых HTTPS-аудиопотоков. `yt-dlp` — внешний исполняемый файл, поэтому используйте его только с доверенными URL и своевременно обновляйте.

**Обновление yt-dlp:** новые версии не устанавливаются автоматически. При необходимости загрузите свежий официальный релиз с повторной проверкой SHA-256. Для ручной диагностики: `yt-dlp --version` и `sudo journalctl -u universal-media-proxy -n 100 --no-pager`. Некоторые сайты могут требовать дополнительные зависимости или авторизацию; установка `yt-dlp` не гарантирует успешное извлечение всех видео.

## 9. Обновления UMP и резервное копирование

При установке можно включить автоматическую проверку GitHub Releases (по умолчанию выключена), выбрать публичный репозиторий `owner/repo` — по умолчанию `Acobat12/universal-media-proxy` — и интервал проверки 1–168 часов (по умолчанию 24). Механизм обновления ожидает **опубликованный релиз** с `ump-release.tar.gz` и `ump-release.tar.gz.sha256`; простой коммит в `main` не запускает обновление. Контрольная сумма, размещённая в том же репозитории, **не является независимой криптографической подписью издателя**.

Обновлятор делает резервную копию и пытается откатиться при ошибке, однако проверка работоспособности после перезапуска не заменяет полноценный HTTP-запрос `/health` и интеграционные тесты. До проверки на реальном VPS рекомендуется оставлять автообновление выключенным.

**Перед переустановкой или обновлением** сохраните:

- `/etc/universal-media-proxy.env` (секреты, не публикуйте файл);
- `/opt/universal-media-proxy` и unit-файлы systemd;
- регистрации, cookies, браузерные профили и другие постоянные данные, включая пути из `TIKTOK_REGISTRATIONS_FILE` и `TIKTOK_PROFILE_DIR`;
- при необходимости конфигурацию Caddy и обновлятора.

Не используйте `rm -rf /var/cache/universal-media-proxy` для очистки только медиа: этот родительский каталог может содержать регистрации и профили TikTok. Очищать допустимо **только отдельно проверенный каталог `DISK_CACHE_DIR`**, когда служба остановлена и файлы не используются.

## 10. Удаление и чистая переустановка

1. Остановите и отключите `universal-media-proxy`, сохраните резервную копию и убедитесь, что она читается.
2. Сохраните постоянные данные отдельно от временного медиакеша.
3. Переместите старый каталог кода и конфигурацию в `.old` вместо немедленного удаления.
4. Склонируйте проверенную версию репозитория, проверьте `bash -n install.sh` и запустите `sudo bash install.sh` из корня проекта.
5. Проверьте `/health`, журнал systemd, доступность HTTPS и реальные медиа для нужных адаптеров; лишь после этого удаляйте старую копию.

**Не удаляйте Caddy, правила UFW, SSH-конфигурацию или пользователя `ump` без проверки других служб.** Для новой установки на том же VPS существующие Fail2ban/UFW могут оставаться настроенными; не требуется сбрасывать firewall.

## 11. Ограничения и безопасность

- `/api/resolve` возвращает стабильный адрес медиа, не требующий токена. Публичный сервер следует защищать ограничением запросов на уровне инфраструктуры.
- Публичные маршруты VOT не требуют API-ключа. Учитывайте риск злоупотреблений: при необходимости ограничивайте доступ, частоту запросов и нагрузку средствами Caddy или сетевой инфраструктуры.
- Квоты передачи в текущей версии учитываются процессом Node.js и могут сбрасываться при перезапуске.
- Любой внешний источник (Bilibili, TikTok, Douyin, NHK, Cloud Mail.ru и другие) может менять API, CDN, требования к cookies, подписи и региональные ограничения.
- При использовании CDN оплачивается **исходящий трафик VPS**, если он не включён в тариф.
- Для публичной эксплуатации нужны дополнительные нагрузочные, сетевые и интеграционные испытания.
- Проверяйте соблюдение условий использования источников и применимого законодательства.

## 12. Разработка и тесты

Для локального запуска требуется Node.js **22+**:

```bash
npm test
npm run check
```

Сервер запускается через `npm start` после установки переменных окружения (сам Node.js файл `.env` автоматически не загружает). На VPS это делает `systemd` через `EnvironmentFile`.

Проект включает набор адаптеров, диспетчер их загрузки, потоковый и параллельный прокси, RAM/SSD-кеширование и необязательный VOT-шлюз. Лицензия MIT — см. `LICENSE`.


### Проверенные изменения для исходников VOT

См. [инструкцию подключения UMP к VOT](docs/VOT_CODE_CHANGES_RU.md). Для UMP используется Protobuf Envelope. Адрес сервера задаётся в настройках VOT; `src/index.ts` менять не нужно.

## Подключение нового сайта одним файлом

Добавьте `src/adapters/имя.js` с `export default` (поля `id`, `matches(url)`, `async resolve(url, context)` и, при необходимости, `mediaHosts: ['cdn.example.com']`) и перезапустите сервер. Новые адаптеры автоматически загружаются; для работы через `/api/resolve` адаптер также должен реализовать `stableMediaPath()` и `resolveMediaPath()`; список отображается в `/health`. Резервные `.bak` игнорируются. Подробный пример: [`src/adapters/README.md`](src/adapters/README.md). Отдельные маршруты и способы регистрации некоторых сайтов остаются логикой их адаптеров.

## Параллельная загрузка медиа по умолчанию

Для некоторых постоянных медиаадресов сервер сначала пытается использовать параллельную загрузку независимо от переданного параметра `mode`. Поведение может отличаться у специализированных адаптеров. Временные медиа-токены не создаются. Если CDN не поддерживает HTTP-запросы диапазонов байтов (Range), загрузчик автоматически переключается на один поток. Переменные `PARALLEL_THREADS` и `PARALLEL_CHUNK_BYTES` задают число параллельных запросов и размер части. Специальные медиа-маршруты Douyin также сначала пытаются использовать параллельную загрузку.

## Постоянные медиаадреса и сохранение перевода

Сервер **не создаёт временные медиа-токены**: модуль `src/core/token.js` и маршрут `/media/<token>` удалены. `POST /api/resolve` возвращает постоянный URL только для адаптеров, поддерживающих `stableMediaPath()` и `resolveMediaPath()`. Bilibili поддерживается; Douyin использует отдельную регистрацию `/api/douyin/register` и `/media/douyin/<awemeId>/audio.mp4`. Регистрация Douyin хранится в памяти и не переживает перезапуск процесса.

Постоянный адрес сам по себе не гарантирует сохранение перевода: VOT/Yandex могут формировать ключ кеша из дополнительных параметров. Для корректной идентификации сохраняйте оригинальный URL видео в VOT. Прокси не хранит готовые переводы Яндекса в своём SSD-кэше.


## Интеграция с VOT

Инструкция для текущего форка VOT: [docs/VOT_CODE_CHANGES_RU.md](docs/VOT_CODE_CHANGES_RU.md). Для Bilibili в описанной интеграции нужны Helper и обработка `.m4a` через Protobuf-клиент. Для других сайтов требуются соответствующие адаптеры/Helper и проверка протокола; универсальная совместимость VOT не гарантируется.

## Текущее состояние проверки

Локальные модульные тесты и HTTP `/health` не заменяют проверки на VPS. На реальном сервере отдельно проверьте доступность исходных сайтов, работу FFmpeg/Chromium, выдачу Range, TTL, общий бюджет медиакеша, сохранность регистраций и работу VOT. Известное ограничение универсального хранилища: автоматическая очистка произвольных имён и форматов файлов нового адаптера пока не гарантирована; адаптер должен использовать API `createAdapterMediaStorage`, учитывать активные файлы и придерживаться поддерживаемых правил менеджера. Полная унификация остаётся задачей дорожной карты.
